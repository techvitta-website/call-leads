Super Admin & Security Hardening

sales.techvitta.in · deployed 29 July 2026

venkatesh@techvitta.in is now a Super Admin — a fourth role above Owner, with access to every page in the application. Getting there surfaced a serious hole, which is the first thing below.

The critical finding

Anyone with a login could make themselves a super admin.

The database rule controlling profile edits allowed you to update your own row. That is reasonable for changing your name or phone number — but the rule said nothing about which columns, and a person's role lives in that same row. So any salesperson could send one request straight past the application: 

PATCH /rest/v1/users?id=eq.<their own id>
{"role": "super_admin"}

I tested this against your live database. It returned success and the role changed. Every permission check I had built into the app was bypassable this way, because the browser never had to go through the app at all.

It is now closed with two independent defences: the database no longer grants ordinary users permission to write the role, account-status or lead-routing columns at all, and a separate rule rejects any such change regardless of what permissions say. Both would have to fail for the hole to reopen. Editing your own name and phone number still works normally.

Why the owner needed fixing before a tier could sit above it

Owner was nominally the top role but wired as the weakest. Three separate causes:

Ten pages Clients, Quotations, Invoices, Receipts, Suppliers, Purchase Orders, Won Deals, Lost Deals, Deal Stages and Follow-ups each checked for manager exactly and redirected an owner away. The landing page then bounced them back, so it looped silently with no explanation.
36 database rules Each listed the permitted roles by name. A new tier would have arrived with less database access than a manager. All 36 now ask a single shared function instead, so the hierarchy is defined in one place.
The sidebar Owner had seven menu items to the manager's ten, with no route to projects, automations, sequences, invoicing or purchasing.

The lock that has no key

No role below super admin may grant super admin. That makes losing the last one unrecoverable without direct database access, so the system refuses to demote, suspend or delete the only super admin who can actually sign in. Promote a second one first and the guard stands down.

The salesperson URL hole

Access control was previously written page by page, and the shared route guard only checked that somebody was signed in. A salesperson who typed /leads or /revenue saw every lead in the business and all revenue data. All 45 protected routes now declare who may open them, and a refusal says so plainly instead of bouncing you around.

Dashboard statsThe summary view was readable without signing in. Revoked.

TeamsA salesperson could create a team that then appeared in management reporting. Now staff only.
Account rowsAnyone could delete their own profile row, orphaning their leads. Now administrators only.

How this was verified

Four throwaway accounts, one at each tier, tested against the live project and deleted afterwards. The database was confirmed back to its exact prior state — 16 profiles, 9 logins, 131 leads.

Turn on leaked-password protection in the Supabase dashboard (Authentication → Policies) — it checks new passwords against known breach lists and is the one advisor warning I cannot fix from here.

Separately: every signed-in person can still read the staff list — names, emails and roles. That is ordinary directory information and the app relies on it to show who a lead is assigned to, so I left it alone. Tell me if you would rather it were restricted.
